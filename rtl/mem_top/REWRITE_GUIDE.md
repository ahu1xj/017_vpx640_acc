# mem_top 复写指南（练手用）

> 目标：**自己从零写一版 `dma_axi4_master`**，练 RTL 设计能力。
>
> 方法：**规格驱动**——先钉死接口与验收标准，自己设计内部实现，用现成的 tb 验收。
> **不要先读原码**（原因见 §1）。

---

## 0. 什么叫"复写成功"

**一句话：现有 tb 一行不改，跑出同样的数字。**

```
验收命令:  vivado -mode batch -source vivado_tb/add_sim_tb.tcl -tclargs CASE=0
验收判据:  日志出现 MEM_TOP_TB_PASS
          且三个数字与基线完全一致
```

**512 位宽的基线（已实测）**：

| 指标 | 数值 |
|---|---|
| 写突发总数 | **81** |
| 读突发总数 | **74** |
| 下发命令数 | **25** |
| TB 检查错误 / 读回比对错误 / 假 DDR 断言错误 | **0 / 0 / 0** |

**其他位宽的预期值**（自己先推一遍，再和实测对）：

| 位宽 | 写突发 | 读突发 | 约束来自 |
|---|---|---|---|
| 512 / 256 / 128 | 81 | 74 | 4KB 边界 |
| **64** | **149** | **143** | ★ **256 拍上限** |

> 64 位那行是重点：约束从"4KB 边界"变成"突发拍数上限"。
> 两组数字都对上，说明"三取最小"的规则在两种约束下都正确。

**为什么要对数字**：功能 PASS 只说明"数据对"，突发数一致才说明**切分策略**也一致（地址序列、每段的长度）。这是"等效复写"的判据。

## 1. 为什么不先读原码

```
读原码再写  →  变成抄写，学不到设计决策（因为答案已经给了）
规格驱动写  →  你必须自己决定：怎么缓冲、怎么流水、怎么仲裁
               卡住了再去看原码的某一处 → 那才是有效的对照学习
```

**但也有不能被"自由发挥"的东西**——接口和外部行为是合同，见 §2。合同之外的内部结构，全由你定。

**规格从哪来**（不用看实现）：

| 规格 | 来源 |
|---|---|
| 端口 | `rtl/top/cnn_acc_top.v` 的例化处（谁连谁、什么位宽） |
| 命令格式 | `rtl/store_top/store.v` 里拼命令的那一行 |
| 行为约束 | AXI4 协议 + 本工程的约定（§2.3）|
| 验收行为 | `vivado_tb/mem_top/mem_top_tb.v`（读得懂 tb 就读懂了合同）|

## 2. 合同（不可变部分）

### 2.1 端口

照抄现有端口表（**名字、方向、位宽一个都不能变**）：

```
时钟复位:  clk(ui_clk) / usr_clk(dma_clk) / rst_n
命令入口:  s_axis_wrcmd2_*  (64b, usr_clk 域)
          s_axis_rdcmd2_*  (64b, usr_clk 域)
数据入口:  s_axis_wrddr_*   (512b, usr_clk 域)
数据出口:  m_axis_rdddr_*   (512b, usr_clk 域)
AXI4 主口: m_axi_aw/w/b/ar/r (clk 域)
```

**关键：两个时钟域**。命令和数据在 `usr_clk` 侧，AXI 在 `clk` 侧 → 你必须做跨域。

### 2.2 命令格式

```
CMD2 = { cmd[63:32], cmd[31:0] }
         └─ 地址 ─┘  └─ 字节数 ─┘      （注意：长度是字节，不是拍）
```

### 2.3 行为约束

| # | 约束 | 说明 |
|---|---|---|
| 1 | **突发不得跨 4KB** | AXI 协议硬性要求 |
| 2 | **突发 ≤ 256 拍** | AXI4 上限 |
| 3 | **AW 与 W 同拍启动** | 本工程的约定（`wr_beat_m_tready` 门控于 `w_active`）|
| 4 | **app 侧固定 512b** | 每拍 64 字节，`AXI_DATA_WIDTH` 只影响 AXI 侧 |
| 5 | **位宽可参数化** | 64/128/256/512 四档都要能跑 |
| 6 | **命令接受后不回退** | 收到就给下游 ready，不依赖下游 |

## 3. 分阶段实现（每阶段都能独立验证）

**核心方法：把大设计拆成能单独跑 tb 子集的小步，每步都用现有 tb 验。**

| 阶段 | 做什么 | 用什么验 | 验收 |
|---|---|---|---|
| **S0** | 骨架：端口 + 空状态机，编译过 | `CASE=1` | 编译通过，不挂死（会 FAIL，但要有输出）|
| **S1** | **单笔写 + 单笔读**，长度 ≤4KB、4KB 对齐 | `CASE=1` | 写突发 1 / 读突发 1、数据一致 |
| **S2** | **长传输**：>4KB 时拆多条突发 | `CASE=2` | 写突发 1+1+1+2=5 / 读 5 |
| **S3** | **跨 4KB**：按边界切开 | `CASE=3` | 写 2 / 读 2，且波形上地址断在边界 |
| **S4** | **位宽参数化** | `CASE=0` + 改 define | 四档都跑，数字见 §0 |
| **S5** | **读写并发**（共用一条 AXI 口）| `CASE=4` | 背靠背 8 条写 + 1 条读 |
| **S6** | **缓冲与反压** | `CASE=6`（`rdy_delay=8`）| 慢 ready 下仍正确 |
| **S7** | 全量 | `CASE=0` | **81 / 74 / 25 / 0 / 0 / 0** |

**为什么这个顺序**：S1~S3 是切分逻辑（最难最核心），先把它做对；S4 是参数化（机械）；S5~S6 是时序/流控（工程性）。**每一步只引入一个新概念。**

## 4. 需要你自己拿主意的设计决策

**这些没有标准答案**——原码也只是其中一种选择。想清楚再动手：

### 4.1 命令怎么接

```
□ 命令 FIFO 多深？（原工程 16）
□ 什么时候给 s_axis_wrcmd2_tready？
   - 一直接（简单，但命令可能丢）
   - 有空位才接（安全，要计数）
   - 一条做完才接下一条（最保守，吞吐低）★ 想清楚这条对突发数有影响吗
```

### 4.2 拆分成什么

```
□ 中间层抽象：命令 → 描述符（{地址, 拍数}）→ AXI 突发
   要不要这一层？（原工程有，但你可以不做）
   做的好处：地址算术与 AXI 时序解耦，容易分别验证
   不做的代价：状态机里地址和握手搅在一起

□ 描述符生成是"一个状态机逐个吐"还是"流水式每拍一个"？
   前者简单，后者吞吐高但时序难
```

### 4.3 地址算术

```
□ 位宽：32 位够吗？（原工程 32，受 4GB 限制）
□ 4KB 边界的"距离"怎么算？
□ 逐步推进用累加器还是每拍乘法？（关系到时序收敛）
```

### 4.4 读写怎么共用一条 AXI 口

```
□ AW 和 AR 独立通道，本能并发
□ 但 W 和 R 的数据 FIFO、以及 B 响应要不要仲裁？
□ 写和读谁优先？饥饿了怎么办？
```

### 4.5 缓冲放哪、多深

```
□ 命令（64b）、数据（512b）各要几条 FIFO？
□ 深度怎么定？——★ 取决于你要容忍多大的下游延迟
   （这正是 §6 的实验②要回答的问题）
□ 用同步 FIFO 还是异步？哪个位置必须异步？
   （提示：命令和数据在 usr_clk，AXI 在 clk）
```

### 4.6 反压策略

```
□ 上游 ready 依赖什么？
   - 依赖下游 ready  → 组合路径穿透，时序差
   - 只看本地占用    → 需要计数/信用机制（原工程用 credit）★ 推荐
□ 深度不够时怎么办：丢数据（不可接受）还是反压（正确）
```

### 4.7 位宽适配放在哪一层

```
□ 512b app 拍 → AXI 拍：拆分点放"命令层"还是"数据层"？
   （放数据层 = 每拍拆 N 份；放命令层 = 描述符里就换算好拍数）
□ 两种做法对 §0 的突发数有影响吗？（想清楚再实现）
```

## 5. 已知的坑（我在这套代码里踩过的）

| # | 坑 | 症状 | 为什么 |
|---|---|---|---|
| 1 | **B 通道寄存器没复位** | `awready` 变 `x` → 写通道**死等**，仿真卡住 | 组合逻辑依赖了未复位的寄存器；所有参与握手决策的 reg 都必须复位 |
| 2 | **4KB 检查的边界含不含** | 误报（把合法的报成违规）| 末字节落在 0xFFF 是**合法**的，判据是 `起始偏移 + 总字节 > 4096`，不是 `>=` |
| 3 | **长度单位** | 突发数全错 | CMD2 的长度是**字节**；AXI 的 `awlen` 是**拍数-1**；app 拍是 64 字节。三个单位别混 |
| 4 | **AW 与 W 的时序** | 上游等 W、下游等 AW → 死锁 | 本工程约定 AW/W 同拍启动；你的从机/激励要按这个来 |
| 5 | **FIFO 的 data_count 语义** | 流控差 1 拍 | 有些 FIFO IP 的 count **不含**输出寄存器里的那个字；用 count 做水位判断时必须确认 |
| 6 | **位宽切换后约束变了** | 突发数与预期不符 | 64 位时 `256拍×8B = 2048B < 4KB` → 拍数上限取代 4KB 成为主约束 |
| 7 | **TB 与 DUT 同时间步竞争** | 随机报"末拍未拉 tlast/wlast" | tb 在 `@(posedge clk)` 后立刻改信号，DUT 同一边沿读到新值；tb 侧要 `#1` |

## 6. 验证手段

### 6.1 复用现有 tb（不改一行）

```
vivado_tb/mem_top/mem_top_tb.v        用例 + 四项检查
vivado_tb/mem_top/axi4_slave_mem.v    假 DDR + 协议断言器
vivado_tb/README.md                   怎么跑、看什么
```

**这个 tb 就是你的验收标准**。它检查四件事：数据一致性、AXI 首地址与总字节、协议合规、边界用例。

### 6.2 数字对账法（比 PASS 更强）

不要只看 `PASS`，还要看**突发数**：

```
先按规则手推： 每突发字节 = min(剩余, 到4KB边界距离, 最大突发字节)
再和日志的 "写突发 N 条, 读突发 M 条" 对
```

**数字对上 = 切分策略一致**；数字不对但 PASS = 你的实现走了另一条路（可能更优也可能有隐患）。

### 6.3 看波形确认切分

单跑 `CASE=3`（跨 4KB），波形上确认地址**正好断在 4KB 边界**。

### 6.4 提前发现"没写东西"

`CASE=1` 跑出 `写突发 0 条` → 说明命令根本没被接受，先查握手，别急着查地址。

## 7. 什么时候可以去看原码

```
□ 允许：某个阶段卡住超过半天，只看**那一处**（比如"它怎么生成描述符的"）
□ 允许：S0~S7 全部跑通后，做对照学习
□ 不建议：S1 还没跑通就通读全部 1095 行
```

**跑通后对照清单**（这才是复写的最大收获）：

| 对照项 | 问自己 |
|---|---|
| 命令接受策略 | 我何时给 ready？原码呢？哪个对突发数/吞吐更有利？ |
| 拆分层次 | 我用了几层状态机？原码用了几层？为什么？ |
| 地址算术 | 我用累加还是乘法？原码为什么在某个位置改用累加器？（注释里有线索）|
| 缓冲深度 | 我凭什么定的深度？原码的 7 个深度参数依据是什么？ |
| 反压 | 我的上游 ready 依赖下游吗？原码呢？ |
| 防错 | 我加了哪些编译期/运行期检查？原码那种"例化不存在的模块"手法你想到过吗？ |
